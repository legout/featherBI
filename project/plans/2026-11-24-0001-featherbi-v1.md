## Goal

Ship the featherBI skill. An agent writes `dashboard.yaml`, and `build` deterministically produces a single-file dashboard that meets spec 0001 acceptance 1–9. Acceptance 10 is a manual check by the owner.

## Runtime and layout (from ADR 0002)

```text
skill/featherbi/                 # the installable skill (npx skills add legout/featherbi)
  SKILL.md                       # agent workflow: profile -> write config -> build -> report
  references/                    # config schema doc, presets catalog, sources/handoffs, troubleshooting
  scripts/featherbi.mjs          # one entry: `profile`, `build` (Node >= 22, no npm deps)
  scripts/lib/*.mjs              # config load/validate, source phase, tile validation, render
  templates/dashboard.html       # page shell
  assets/renderer.js             # generic browser renderer (engine adapter, filters, tiles)
  assets/presets/*.json          # ECharts preset options + required-column contracts
  assets/app.css                 # prebuilt DaisyUI 5 + Tailwind 4 CSS (release artifact)
  assets/vendor.lock.json        # pinned CDN URLs + SHA-384 integrity of every JS library
  assets/perspective-charts.patched.js   # release artifact, built by tools/
  schema/dashboard.schema.json   # JSON schema of dashboard.yaml
tools/                           # release-time only: build CSS, apply/verify Perspective patch, refresh vendor.lock, fixtures
tests/                           # node:test + Playwright journeys (dev only)
fixtures/                        # hand-worked + volume + per-format source fixtures
```

- **Tools:** the build uses the DuckDB CLI (≥ 2.0; tested on 2.0.x) through `execFileSync`, and YAML is parsed with a small vendored parser (the `yaml` package copied into `scripts/lib/vendor/`, with its MIT license).
- **Dev-only (`tools/`, `tests/`):** npm with Playwright and Tailwind. CI runs on GitHub Actions with Chrome and Firefox (Playwright), Node 22 and the DuckDB CLI.
- **Reuse:** the prototype probes (see [research](../research/2026-11-24-dashboard-stack.md), `~/.local/state/factory/featherbi/proto/v3/`) are references only. Their code is not copied in wholesale.

## Tasks

Tasks run in order T1 → T2 → T3 → T4. After T4, T5, T6 and T8 can run in parallel; they touch separate renderer modules and preset files. T7 runs after T2. T9 runs after T5, T6 and T8. T10 runs after T9, and T11 comes last.

### T1: Tracer bullet, from config to an opened dashboard with one KPI

- **Files:**
  - `skill/featherbi/scripts/featherbi.mjs` (`build`);
  - `scripts/lib/{config,render}.mjs`;
  - `templates/dashboard.html`;
  - `assets/renderer.js` (engine adapter + KPI only);
  - `assets/vendor.lock.json`;
  - `tools/build-css.mjs` and `assets/app.css`;
  - `fixtures/hand/` (12 sales rows plus `targets.xlsx`, with hand-computed values in `README.md`);
  - `tests/journey.spec.mjs`.
- **Behavior:**
  - `build dashboard.yaml` reads one `read_parquet` source with the native DuckDB CLI and writes the snapshot table with `ORDER BY ALL` and fixed Parquet options.
  - It embeds the snapshot as base64 and writes `dist/<name>.html`.
  - On open, the page boots Haybarn-Wasm (pinned in `vendor.lock.json`) through the engine adapter and renders the KPI.
  - The page uses the DaisyUI layout and theme toggle.
  - The engine adapter exposes `{open(snapshots), query(sql, params)}`. The Haybarn bundle is assembled by hand and uses an `apache-arrow` import map.
  - Upstream duckdb-wasm can be selected with `engine: duckdb-wasm`.
- **Validation (normal risk):** Playwright opens `file://…/hand.html` in Chrome. The Revenue KPI must equal the hand total in `fixtures/hand/README.md`, and the console must show no errors. This is a `new-test`: it becomes the journey harness that later tasks extend.
- **Done:** that journey is green on CI.

### T2: Source phase for every handoff, and `profile`

- **Files:** `scripts/lib/sources.mjs`; the `profile` command; `fixtures/formats/` with one fixture each of CSV, JSON, Parquet, XLSX, SQLite, Delta, Iceberg (metadata file) and DuckLake (local catalog). Each fixture holds a known count and sum, recorded in its README.
- **Behavior:**
  - **Source config:** each source is `read` (a table expression) or `attach` (`postgres:` / `sqlite:` / `ducklake:`) plus `table` or `sql`.
  - **Extensions and secrets:** the build installs and loads the extensions it needs in the native session. Secrets come only from the environment or DuckDB secrets; the build refuses any config key that looks like a credential (`password`, `secret`, `key_id`, `token`).
  - **Snapshot output:** every snapshot gets an added `__row` column, the row number after `ORDER BY ALL`.
  - **`profile <source…>`:** prints the schema, the row count and 5 sample values per column as JSON.
- **Validation (normal risk):** a node:test builds every format fixture into snapshot Parquet and compares each count and sum with its README (`new-test`; protects acceptance 9 against a source format silently dropping rows). Profiling the hand fixture is checked by eye only.
- **Done:** every format fixture reaches its snapshot with the expected count and sum.

### T3: Tile SQL contract and build-time validation

- **Files:** `scripts/lib/validate.mjs`; `schema/dashboard.schema.json`; `tests/validate.test.mjs`.
- **Behavior:**
  - **Schema validation** checks `dashboard.yaml` with a small built-in validator. No dependency, and only the keywords the schema uses.
  - **Execution.** Every tile SQL runs in a native session where only the snapshot tables are attached, `autoload_known_extensions` and `autoinstall_known_extensions` are false, and `enable_external_access` is false. Each runs twice: once with all placeholders as no-ops, and once with one sample value per declared dimension plus the default date range.
  - **Result contract.** The result columns are checked per tile type. Presets declare their required columns in `assets/presets/*.json`.
  - **Rejection.** The build stops on any of these, naming the tile id and the cause:
    - an unknown type or preset;
    - a missing column;
    - a click on an undeclared dimension;
    - a table column not in its source;
    - SQL that fails or references something outside the snapshot;
    - `--offline` combined with `--split`.

    No HTML is written.
- **Validation (normal risk):** a node:test runs one table-driven case per rejection listed in spec §Tile types and in acceptance 8, including an aliased join with an unqualified placeholder. Each case expects its message, and no `dist` output (`new-test`; the error contract is user-facing and easy to regress).
- **Done:** every case passes.

### T4: Filter model, placeholders and the state machine

- **Files:**
  - `scripts/lib/filters.mjs` (build side): select options, date anchor, placeholder expansion with alias qualification and per-table `cols`;
  - `assets/renderer.js` filter module (browser side): state, chips, Reset, `exclude`, bound parameters.
- **Behavior:**
  - Follows spec §Filters exactly.
  - Expansion is a pure function `(sql, state, dims, date, tableColumns) → {sql, params}`, shared by the build validation (via Node) and the renderer (the same file is imported by both). A single implementation keeps the build and the browser from drifting apart.
- **Validation (normal risk):** a node:test checks the expansion function. The expected SQL and parameters are hand-written from spec §Filters:
  - no filter;
  - one dimension;
  - an alias;
  - a table missing the dimension;
  - two tables;
  - `exclude`;
  - the date anchor across two tables with different last dates.

  Spec r4 adds (node:test, hand-written from spec §Filters): hash serialization and parsing (valid, undeclared dim, unknown value, reversed date range), and the sequence/coalescing rule (a result for an older sequence number is never painted).

  The journey extends T1 with the selects and Reset on the hand fixture, and acceptance 8a. Both are `new-test`; the expansion is the core correctness boundary.
- **Done:** both are green.

### T5: KPI and ECharts tiles with the 17 presets

- **Files:** `assets/renderer.js` (kpi, echarts and text tile modules); `assets/presets/{line,area,bar,stacked-bar,hbar,pie,donut,scatter,heatmap,treemap,sunburst,funnel,gauge,sankey,waterfall,boxplot,calendar}.json`; `references/presets.md`.
- **Behavior:**
  - Each preset holds an ECharts option template, its required columns and its click key columns.
  - A tile `option` is deep-merged over the preset for styling only. Keys that bind data are rejected by T3.
  - KPI tiles have `value`, optional `compare` (Δ %) and optional `spark`.
  - The ECharts theme follows the light/dark toggle.
  - Clicks set filters per spec, including a two-dimension heatmap click and the toggle-clear.
- **Validation (normal risk):** the journey `tests/presets.spec.mjs` renders all 17 presets on the hand fixture. Each must render a non-empty canvas with no console errors in Chrome and Firefox. This is a `new-test` and the residual-risk check from spec §Tile SQL: native vs. Haybarn function parity for the shipped presets. The journey also checks that the bar tile shows revenue and target per region on the hand fixture.
- **Done:** both are green.

### T6: Pivot and table tiles

- **Files:** `assets/renderer.js` (pivot and table modules); the AG Grid entry in `vendor.lock.json`.
- **Behavior:**
  - **Pivot:** a DaisyUI table built from `r, c, v` plus the optional `r_total`/`c_total` markers, as in spec §Tile types. Data rows are clickable; total rows and columns are not.
  - **Table:** AG Grid Community with the infinite row model. Each page query is `WHERE <filters> ORDER BY <sort>, __row LIMIT ? OFFSET ?`, and the total count uses the same `WHERE`. The table header shows "N rows (filtered)", and the count updates whenever the filters change. The grid theme follows light/dark.
- **Validation (normal risk):** the journey on the hand fixture:
  - the EU × 2025-02 pivot cell equals the README value;
  - clicking EU narrows the pivot, the KPI and the table count;
  - sorting the table by `order_date` and paging with a page size of 5 returns every row exactly once.

  This is a `new-test`; paging with ties is a named regression risk.
- **Done:** green.

### T7: Remote source handoffs (docs and code, verified manually)

- **Files:** `references/sources.md`; the `attach` support in `sources.mjs`, if T2 did not already cover it.
- **Behavior:** documents the handoffs, examples and unqualified status for these sources, as in spec §Sources:
  - Postgres, with `PGPASSWORD` or `~/.pgpass`;
  - pg_lake and pg_ducklake;
  - S3 and SeaweedFS secrets;
  - Iceberg REST;
  - SharePoint, as a synced folder or an anonymous link.
- **Validation (low risk):** a docs review only. Acceptance 10 is the owner's manual check after T11.
- **Done:** every source in the spec table has a documented handoff and an "unqualified until verified" marker.

### T8: Explore

- **Files:** `assets/renderer.js` (explore module); `tools/patch-perspective.mjs`, which pins Perspective 5.10.x, applies the two `blob:` to `data:` patches, fails if an anchor is missing and writes `assets/perspective-charts.patched.js`; the vendor.lock entries.
- **Behavior:**
  - A navbar button, on by default; `explore: false` hides it.
  - The table comes from `explore.table`, defaulting to the first source.
  - Perspective loads lazily on first open, and nothing is fetched before that.
  - Each open applies the filters that apply to that table.
  - Filter changes never re-render it.
- **Validation (normal risk):** the journey on `file://` in Chrome and Firefox:
  - no Perspective requests before the click;
  - after setting region = EU and opening Explore, the viewer's row count equals the EU row count from the README.

  This is a `new-test`, and it guards the `file://` patch against Perspective upgrades.
- **Done:** green.

### T9: Output modes, the size warning and render determinism

- **Files:** the `render.mjs` modes; `tests/outputs.spec.mjs`.
- **Behavior:**
  - **Default:** a single file; libraries come from the CDN with SRI.
  - **`--offline`:**
    - inlines the engine, its wasm, the libraries, the patched Perspective bundle and the fonts;
    - the Wasm and the worker load from `data:` or blob URLs created inside the page;
    - reports the file size.
  - **`--split`:** writes a folder (`dist/<name>/` or `--out <dir>`) containing `index.html` and one Parquet file per snapshot, fetched relative to the page.
  - **Size warning:** emitted above 25 MB of embedded Parquet.
  - **Determinism:** no build timestamps; stable JSON key order; fixed snapshot order (from T2).
- **Validation (normal risk):** all `new-test`; offline and split are separate delivery paths that can each break on their own.
  - **Offline:** the hand fixture is built with `--offline` and opened in Playwright with every non-`file:` request blocked. All tiles must render and Explore must open.
  - **Split:** the hand fixture is built with `--split` and served by `python3 -m http.server`. It must show the same KPI and pivot values as the default build.
  - **Determinism:** two consecutive builds of the hand fixture must give the same SHA-256.
- **Done:** green.

### T10: Skill documentation, install, retire the old package

- **Files:**
  - `skill/featherbi/SKILL.md`, which describes the workflow:
    - profile;
    - pick presets from `references/presets.md`;
    - write the config following `references/config.md`;
    - build;
    - on error, fix the named tile;
    - report the output path and the size;
  - `references/{config,troubleshooting}.md`;
  - `README.md`;
  - `CHANGELOG.md`;
  - `.github/workflows/ci.yml`.
- **Behavior:**
  - **Install:** `npx skills add legout/featherbi` installs exactly `skill/featherbi`.
  - **Old npm package:** npm allows unpublishing an old package only when no other package depends on it, it has under 300 downloads a week, and it has a single owner. If those hold, the owner runs `npm unpublish featherbi --force`; otherwise `npm deprecate featherbi "moved to github.com/legout/featherBI (agent skill)"`. Both need the owner's npm login. T10 checks the conditions (`npm view featherbi`, the dependents count, weekly downloads) and gives the owner the matching command.
- **Validation (low risk):**
  - `npx skills add ./ --list` must show `featherbi`;
  - `node ~/.pi/agent/npm/node_modules/skill-diet/skills/skill-diet/scripts/eval.mjs check skill/featherbi` must report the links as ok.
- **Done:** both checks pass, and the owner has a one-line deprecation command.

### T11: Final verification, acceptance 1–9

- **Fixtures:** the hand fixture; the volume fixture (`tools/gen-volume.sql`, 1 M rows, deterministic, as in the research) plus `targets.xlsx`; the format fixtures.
- **Journeys:** run by `tests/` in Chrome and Firefox; the owner's machine is used only for timing.

  | Acceptance | Check |
  |---|---|
  | 1 | Hand values: totals, EU click, Online select, Reset, the EU × 2025-02 cell. |
  | 2 | The volume dashboard has ≥ 4 KPIs, 3 ECharts tiles, a pivot and a table, plus all the filters. |
  | 3 | `file://` on both browsers with 0 console errors, and Explore shows the EU rows. |
  | 4 | Offline (from T9, reused). |
  | 5 | Split (from T9, reused). |
  | 6 | The soft timing target, measured by `tests/timing.mjs` on the owner's machine and reported as numbers. |
  | 7 | The hand and volume fixtures each built twice with equal hashes. |
  | 8 | The rejection suite (from T3, reused). |
  | 9 | Format fixtures as KPI pairs (count, sum). |
- **Reuse:** evidence from T3 and T9 counts as long as the code it covered has not changed since. Otherwise rerun only the affected journey.
- **Done:** a report listing every acceptance item as pass, fail or measured, with the commands used.

## Residual risks and manual checks

- **Haybarn is an RC:** the engine adapter allows a switch through config (`engine: duckdb-wasm`).
- **Perspective upgrades** can break the patch; T8's anchor check and its journey would catch that.
- **Safari is not covered;** the owner can spot-check it if needed.
- **Acceptance 10** (Postgres, pg_lake, pg_ducklake, S3, Iceberg REST, SharePoint) is a manual check by the owner on the internal network.
- **Retiring the npm package** (unpublish or deprecate) needs the owner's npm credentials.
