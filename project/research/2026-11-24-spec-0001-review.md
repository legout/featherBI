# Spec 0001 review — fix-first

Reviewed `project/specs/2026-11-24-0001-featherbi-v1.md` at `efbc836` against ADRs 0001/0002, the dashboard-stack evidence, `CONTEXT.md`, and the four settled decisions. References below are to spec line numbers unless noted. The proposed spec is not ready for decomposition: a planner would have to decide the following behavior, not just how to build it.

1. **Multi-source filter semantics are undefined (§ Interaction/Config, lines 49–76).** `region` and `order_date` have one column name each, but the acceptance dashboard combines sales and Excel targets per region. A target may have a region but no date or channel; applying every predicate breaks the query, while ignoring an applicable region filter gives a wrong comparison. Specify where select options come from, how queries bind a dimension/date to their input (including when a dimension is absent), and how selects, clicks, chips, `exclude` and Reset change the same state. In particular, say what a click does when its dimension already has a selection, what a two-dimension heatmap click sets, and what Reset restores. Use one worked multi-source example; leave exact schema syntax to the plan.

2. **Successful SQL is not enough to render a tile (§ Tile types/Config, lines 37–76; acceptance 5).** A pivot query can dry-run successfully yet omit `v`; `r,c,v` alone does not say how subtotal rows are distinguished from data rows or whether clicking a total sets a filter. KPI comparison/sparkline and chart preset inputs likewise have no defined result contract. State the minimum result shape and bindings for each SQL-backed tile, how JSON `option` relates to the selected preset, and what the builder rejects before emitting HTML. Bound the named map preset to the geography it ships or the data the author must supply; the chart library alone does not supply that contract. For the infinite table, specify that the current row set is filtered and ordered before paging and that consecutive pages must not duplicate or omit rows when sort values tie. Keep this to the declared tile types and a small set of supported interactions, not a new query language.

3. **Default Explore has no default table (§ Tile types/Settled decisions, lines 47, 113).** The sales-plus-targets example does not choose a table, but it must get Explore without extra config. Specify which snapshot table is used by default, how the author chooses another, and which filters apply to it. Say what happens on reopen after a filter changes; ADR 0001 and `CONTEXT.md` rule out re-rendering Explore on the ordinary filter path. Extend the `file://` opening example to open Explore and check that it shows the expected filtered rows. Merely rendering the tiles does not exercise the lazy worker path for which the research required a patch.

4. **Output modes lack opening contracts (§ Outputs and acceptance 2, lines 31–35, 102, 111).** The only double-click example covers an embedded file. An author following the 25 MB warning may send a split folder and expect the same workflow, but the probe only demonstrated embedded `file://` data; loading sibling Parquet is a different browser operation. State the supported opening context for split output, whether `--split` and `--offline` can be combined, and how the promised output filename/location is chosen (`dist/<name>.html` versus `dashboard.html`). Give offline output an observable no-network criterion, including first opening Explore; give split output a criterion that its separate Parquet loads in its documented context. Preserve the default double-click journey.

5. **Source and tile SQL have different execution boundaries (§ Sources/Config, lines 23–29, 58–76; acceptance 6).** The native CLI can run queries that need extensions or sources that Haybarn cannot access (the probe documents Postgres and Delta). A native dry run is not by itself proof that a tile is a snapshot-only query. Explicitly separate native source SQL and browser tile SQL, which may query only named snapshots, and state what validation guarantees. Also define what build-ready SharePoint/OneDrive URL means: a browser login does not authenticate a subsequent DuckDB CLI process. Document the supported handoff (e.g. a synced file or a URL already readable by the CLI) and the Postgres credential handoff without putting secrets or connection configuration in the recipient artifact. For the promised DuckLake, Iceberg REST and SharePoint/OneDrive paths missing from acceptance 6, name a local or manual acceptance route or mark the path unqualified; do not add OAuth or internal-server CI.

6. **The byte-identity guarantee has unstated inputs (§ Config/Determinism, lines 63–64, 66, 78–82; acceptance 4).** Valid native source SQL as currently described can depend on the clock or return rows with no stable ordering. Identical source files can then produce different embedded Parquet. Define the guarantee's preconditions (repeatable source SQL, stable ordering, compatible tool versions) or what non-repeatable input is rejected; resolve when `last_12_months` is evaluated and what date anchors it. Reconcile the spec's native `2.0.x` execution claim with its `≥ 2.0` prerequisite: distinguish the tested range from what later CLIs are promised to support. A hash check on one fixture cannot establish the unconditional claim.

7. **The main acceptance example checks inventory, not the requested answer (lines 96–106).** The example passes if the agent produces the right number of tiles while ignoring the Excel targets or rendering identical totals after a click. Specify where revenue by region/month and the target comparison appear and include one known result before and after a named filter/click. Keep the 1 M-row journey for opening and the owner's soft timing target; correctness can use a tiny hand-worked slice. Likewise, the local source example should verify known snapshot-backed values rather than only a successful exit, so an omitted source cannot pass.

**Security: n/a for attack findings.** The stated flow does not establish an attacker-controlled path into executable config; the SQL phase and credential handoff above are unresolved product contracts, not a claimed exploit.

**Disposition: hand back for spec fixes.** No repo edits, implementation, or runtime checks. Firefox, offline delivery, and full native-source coverage are not established by the probe; the soft speed target is not a blocker.

## Recheck (5068ca8)

1. **Not resolved** — The worked sales/targets example and shared state are clear, but the placeholder contract does not bind predicates to aliased tables in joins or define one date anchor across multiple dated tables.
2. **Not resolved** — The contracts now cover result columns, map scope, and paging, but the new pivot total rule contradicts accepted ADR 0001.
3. **Resolved** — Explore defaults to the first source, takes applicable filters on every open, and is exercised with filtered rows on `file://`.
4. **Not resolved** — The opening contexts and mode checks are explicit, but split output has no defined destination under the stated filename and `--out` rules.
5. **Resolved** — Native source SQL and snapshot-only tile SQL have separate contracts, bounded validation, and documented credential handoffs and qualification routes.
6. **Not resolved** — The repeatability conditions and CLI support are clearer, but the new `order_by` override can defeat stable snapshot order.
7. **Not resolved** — The main example now checks real totals and filter effects, but it omits a monthly value assertion, and the local-source example asks one scalar KPI to show both count and sum.

### Remaining blockers

- **1 — Filter bindings (spec lines 48–60, 145–153).** In a join of `sales AS s` and `targets AS t`, both with `region`, a bare `region` is ambiguous and `sales.region` is not visible under the alias. The no-op dry run can pass while a real selection fails. Define a legal way to qualify the relation for each placeholder (or restrict joins to unaliased relations) and validate the expanded binding. Also specify which latest date anchors the shared default when two dated sources end on different days; otherwise authors can get different visible totals from the same dashboard request.
- **2 — Pivot totals (spec lines 77, 212; ADR 0001 § Decision 4).** The ADR assigns pivot aggregation to DuckDB `GROUPING SETS`; revision 2 forbids SQL totals and assigns sums to the renderer. Summing cell averages, for example, does not produce the average across the subtotal's rows. Keep SQL totals with explicit total markers, or get owner approval for the ADR change before planning the renderer-side rule.
- **4 — Split destination (spec lines 19–21, 99–105).** A caller using `--split --out reports/sales` cannot tell whether that path names a folder or an HTML file. State the default split folder and that mode's `--out` behavior so the author knows which folder to serve and share.
- **6 — Ordered snapshots (spec lines 110–119, 194).** A source ordered by `order_date` can have distinct sales on the same day. Ties may change their order and assigned `__row` values across repeat builds, breaking byte identity even with the same inputs. Drop the override or require stable tie-breaking by the remaining row values.
- **7 — Acceptance oracles (spec lines 167–181, 196–199).** Assert one actual region/month pivot value from the hand-worked fixture so an incorrect monthly rollup cannot pass merely by showing only EU. For source qualification, use two scalar KPIs per source (or another already-defined tile shape) so both count and sum can be verified without inventing a new KPI contract.

**Disposition:** Hand back the surviving contract decisions to the owner; no repairs or third round. Spec delta only; no runtime checks. Security: n/a for attack findings.

**Verdict: fix-first.**
