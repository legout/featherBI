## Goal

featherBI is an agent skill. A user describes the dashboard they want ("revenue by region and month from these files"). The agent writes one **dashboard config**. Deterministic scripts and templates then turn that config into an impressive, fast BI dashboard in **one HTML file**. The recipient opens the file by double-click and can filter, cross-filter and explore it without a server.

## Users and flow

1. **The author asks an agent with the skill installed.**
   - The agent profiles the sources with a script that outputs schema, counts and sample values.
   - It writes `dashboard.yaml`.
   - It runs `build`.
   - Every step after writing the config is deterministic.
2. **`build` creates the snapshot.** It has two phases:
   - **Source phase (native):** the DuckDB CLI reads every source and writes one Parquet **snapshot table** per source.
   - **Render phase:** the template, the prebuilt CSS, the renderer, the config and the snapshot become `dist/<name>.html`. `<name>` is the kebab-case `name` from the config (default: the title), and `--out <path>` overrides it.
3. **The recipient opens the file.** Haybarn-Wasm loads the snapshot tables. Tiles render from **tile SQL**, and filters re-run that SQL.

## Scope

### Sources (source phase only)

Each source is a name plus a DuckDB table expression or query, run by the native CLI. Source SQL may use any DuckDB extension. It is never shipped to the browser.

| Source | Supported handoff | Acceptance route |
|---|---|---|
| CSV, JSON, Parquet, Excel (.xlsx) | local path | local fixture (CI) |
| SQLite | local file | local fixture (CI) |
| Delta, Iceberg (metadata file), DuckLake (local catalog file) | local path | local fixture (CI) |
| Iceberg REST catalog | catalog URI; credentials from a DuckDB secret or the environment | manual, owner's servers |
| Postgres, incl. pg_lake / pg_ducklake | `ATTACH` with host/db in config; the password comes from libpq (`PGPASSWORD`, `~/.pgpass`) or a DuckDB secret | manual, owner's internal network |
| S3, SeaweedFS | URL; credentials from a DuckDB secret or AWS environment variables | manual |
| SharePoint / OneDrive | a path in a locally synced folder, or a URL the CLI can read without an interactive login (e.g. an anonymous share link) | manual; anything else is unsupported |

- Credentials never appear in the config, the snapshot or the HTML.
- The HTML contains only snapshot data and tile SQL.

### Tile SQL (browser)

- Tile SQL runs in Haybarn-Wasm. It may reference **only snapshot tables**, by their source names, and the core DuckDB functions.
- Tile SQL never calls extensions or reaches external locations.
- **Build validation:**
  - The build runs every tile SQL once in a native DuckDB session.
  - In that session only the snapshot tables are visible, extension autoload/autoinstall are off, and external file access is disabled.
  - Every filter placeholder is replaced by a no-op predicate.
  - The result is checked against the tile's result contract (below).
- **Residual risk:** a function that native DuckDB has but Haybarn lacks. The skill's own test suite covers this by rendering every preset in a browser. Per-dashboard builds do not.

### Filters (one filter state)

- **Dimensions.** `dims` declares each filterable dimension with a column name (`col`) and optionally per-table overrides (`cols: {targets: region_code}`). A snapshot table that has none of those columns is **not filtered by that dimension**.
- **Date.** `date` declares one date column, with per-table overrides in the same way. A table without a date column is not date-filtered.
- **Placeholder.** `{{filters:<table>}}` in tile SQL expands to the active predicates that apply to that table. Every value is bound as a parameter. With no active filter it expands to `TRUE`.
  - **Aliases.** When the query uses an alias, write `{{filters:<table> AS <alias>}}`. The predicates are then qualified as `<alias>.<column>`.
  - **Joins.** A query that joins tables uses one placeholder per table.
  - **Validation.** The build validates every tile SQL twice: once with all placeholders as no-ops, and once with one sample value bound for every declared dimension and the default date range. This catches unbound or ambiguous columns.
- **Select options.** Each select lists the distinct values of its dimension across all tables that have it, sorted ascending. The options are computed at build time and embedded.
- **Default date range.** It is anchored on the snapshot, not on the clock.
  - `last_12_months` covers the 12 calendar months ending at the **latest date across all dated snapshot tables**.
  - `all` covers the full range across those tables.
  - An explicit `from`/`to` is also allowed.
- **State.**
  - Each dimension holds at most one value.
  - The date range holds `from` and `to`.
  - A select or a click **replaces** that dimension's value.
  - Clicking the currently selected value again clears it.
  - A two-dimension element (a heatmap cell) sets both dimensions; clicking the same cell again clears both.
  - Each active dimension shows as a chip; × clears it.
  - **Reset** clears all dimensions and restores the default date range.
- **`exclude`.** `exclude: [dim…]` on a tile drops those dimensions from that tile's placeholders, so a tile does not filter itself.

### Tile types and result contracts (the agent selects and configures, never codes)

| Type | SQL result contract | Click |
|---|---|---|
| `kpi` | `sql` → one row, column `value`. Optional `compare` → one row `value`, shown as Δ % vs `value`. Optional `spark` → rows `x, y`, ordered by `x`. | none |
| `echarts` | Each preset declares its required columns. For example: `donut`/`pie` → `name, value`; `bar`/`hbar`/`line`/`area` → `x, y` and an optional `series`; `heatmap` → `x, y, value`; `sankey` → `source, target, value`. | `click: <dim>`, or `click: [<dimX>, <dimY>]` for heatmap. The value of the clicked element's first/second key column is set. |
| `pivot` | Rows `r, c, v`, plus optional total markers `r_total, c_total` (booleans, e.g. `GROUPING(region) = 1`). Totals are computed in SQL, for example with `GROUPING SETS` (ADR 0001); rows with a marker set are the total row or column. Without the marker columns, no totals are shown. The renderer never aggregates. | `click: <dim>` on a data row sets that dimension to `r`. Total rows and columns are not clickable. |
| `table` | `source: <table>`, `columns: […]`, all of them columns of that table. The renderer builds the SQL: filters applied first, then `ORDER BY <sort columns>, __row`, then `LIMIT/OFFSET`. `__row` is a stable row number that the build adds to each snapshot, so consecutive pages never duplicate or skip rows. | none |
| `text` | none (Markdown) | none |

- **Presets in v1 (17):** line, area, bar, stacked-bar, hbar, pie, donut, scatter, heatmap, treemap, sunburst, funnel, gauge, sankey, waterfall, boxplot, calendar.
  - Maps are out of v1, because they need geometry data that the skill does not ship.
- **Options.** `option` in a tile is deep-merged over the preset's option and may only change styling (labels, colors, axis formats). Data bindings come from the preset contract only.
- **Build rejection.** The build rejects any of the following:
  - an unknown preset or tile type;
  - missing contract columns;
  - a `click` dimension that is not declared;
  - a `table` column that is not in its source.

### Explore

- It is on by default; `explore: false` turns it off.
- **Table.** It opens one Perspective viewer on the config's `explore.table`, which defaults to the first source.
- **Filters.** On **every open** it applies the dimensions and date range that are active at that moment and apply to that table. While it is open it is not updated, and the normal filter path never re-renders it.
- **Loading.** Perspective loads only on the first open.

### Outputs

| Mode | Result | Supported opening context |
|---|---|---|
| default | one HTML file with the snapshot and CSS inlined; JS from a pinned CDN | double-click (`file://`) or any web server; network access for the CDN |
| `--offline` | one HTML file with everything inlined (engine, libraries, Perspective). The size is reported. | double-click with **no network** |
| `--split` | a folder (default `dist/<name>/`; `--out <dir>` names the folder) with `index.html` plus one `.parquet` per snapshot table | **only via a web server** (e.g. `python -m http.server` inside that folder); not `file://` |

- `--offline` and `--split` cannot be combined; the build rejects the combination.
- The build warns when the embedded Parquet exceeds 25 MB, and recommends `--split` or aggregating in the source SQL.

### Determinism

The same output is guaranteed under these preconditions:

- the same config and the same skill version;
- the same source data;
- **repeatable source SQL** (no clock functions, no `random()`; the author is responsible for this);
- the same DuckDB CLI version.

Under those preconditions, the build writes a byte-identical HTML file because:

- every snapshot table is written in a fixed order (`ORDER BY ALL`, with no override), with fixed Parquet settings;
- nothing in the output depends on the build time;
- library versions are pinned.

**Tested toolchain:** DuckDB CLI 2.0.x and Node ≥ 22. Later DuckDB versions are supported on a best-effort basis, and byte identity across DuckDB versions is not promised. Dashboard builds need no npm install. The DaisyUI/Tailwind CSS is built at release time and shipped with the skill.

### Layout and safety

- **Layout:** responsive (2 columns on desktop, 1 on mobile), with a light/dark toggle.
- **SQL and identifiers:** filter values are always bound parameters. Identifiers come only from the config's declared dimensions, columns and sources.

### Config (sketch; the plan fixes the schema)

```yaml
title: Sales overview
sources:
  sales:   { read: "read_parquet('data/sales.parquet')" }
  targets: { read: "read_xlsx('data/targets.xlsx')" }          # region, target (no date, no channel)
dims:
  region:  { col: region }
  channel: { col: channel }
date: { col: order_date, default: last_12_months }
tiles:
  - { type: kpi, title: Revenue, format: currency,
      sql: "SELECT SUM(revenue) AS value FROM sales WHERE {{filters:sales}}",
      spark: "SELECT date_trunc('month', order_date) AS x, SUM(revenue) AS y FROM sales WHERE {{filters:sales}} GROUP BY 1 ORDER BY 1" }
  - { type: echarts, preset: bar, title: Revenue vs target by region, click: region,
      sql: "SELECT s.region AS x, SUM(s.revenue) AS y, 'revenue' AS series FROM sales s WHERE {{filters:sales AS s}} GROUP BY 1
            UNION ALL SELECT region, target, 'target' FROM targets WHERE {{filters:targets}}" }
  - { type: pivot, title: Region × month, click: region,
      sql: "SELECT COALESCE(region, 'Total') AS r, COALESCE(strftime(order_date, '%Y-%m'), 'Total') AS c, SUM(revenue) AS v,
            GROUPING(region) = 1 AS r_total, GROUPING(strftime(order_date, '%Y-%m')) = 1 AS c_total
            FROM sales WHERE {{filters:sales}} GROUP BY GROUPING SETS ((region, strftime(order_date, '%Y-%m')), (region), (strftime(order_date, '%Y-%m')), ())" }
  - { type: table, source: sales, columns: [order_date, region, channel, revenue] }
```

In this example, a channel filter narrows `sales` but not `targets` (targets has no channel column). A region filter narrows both, and the date range narrows only `sales`.

## Non-goals (v1)

- Live loading in the browser. That is v2: Iceberg, DuckLake and S3 per source, maybe Grainlift for Postgres.
- A server, scheduled refresh, or authentication inside the dashboard. A refresh is a rebuild.
- Editing dashboards in the browser, or saving viewer state.
- A CLI or npm package as a product; the skill with its scripts is the product.
- Theme engine, map presets, other chart libraries, Mosaic, Plotly.
- Multi-select per dimension, custom tile code, or a query language beyond DuckDB SQL with placeholders.
- Specs, ADRs or process beyond these artifacts.

## Acceptance examples

1. **Correct answer on a hand-worked slice.**
   - **Fixture:**
     - `sales`: 12 rows, regions EU/US, channels Online/Retail, months 2025-01 to 2025-03;
     - `targets.xlsx`: one target each for EU and US.
     - The expected values are hand-computed in the fixture's README.
   - **Steps:** build the sample config.
   - **Expected:**
     - Before any filter, the bar tile shows each region's revenue and target, and the Revenue KPI equals the hand total.
     - After clicking EU in the bar tile:
       - the KPI equals the EU total;
       - the pivot shows only EU rows, and its EU × 2025-02 cell equals the hand-computed value from the fixture README;
       - the table count equals the number of EU rows;
       - the target bar still shows the EU target.
     - After selecting channel Online, the targets are unchanged.
     - Reset restores the totals.
2. **Volume journey.**
   - Same config shape over 1 M synthetic rows (Parquet) plus the targets file.
   - The output has at least 4 KPIs, 3 ECharts tiles, 1 pivot and 1 table, with a date filter, region and channel selects, and cross-filter.
3. **Opening (`file://`).**
   - The default output opens by double-click in current Chrome and Firefox. Every tile renders and the console shows no errors.
   - Opening Explore with region = EU shows only EU rows (the row count matches the fixture).
4. **Offline.** An `--offline` build of fixture 1 opens with all network requests blocked. All tiles render and Explore opens.
5. **Split.** A `--split` build of fixture 1, served by `python -m http.server`, renders the same values as acceptance 1.
6. **Speed (soft target).**
   - On the owner's machine (volume journey), filter changes and cross-filter clicks should render all tiles in **< 1 s**. This is measured from the second change onward, as the median of 5.
   - Initial load should be **< 5 s** on a warm CDN cache.
   - A miss is reported with measurements and does not block acceptance on its own.
7. **Determinism.** Building fixture 1 twice, and the volume journey twice, gives identical SHA-256 hashes.
8. **Config errors.** Each rejection listed under the tile types, plus SQL that fails or references something outside the snapshot, stops the build with an error that names the tile and the problem. No HTML is written.
9. **Local sources.**
   - One build reads one fixture each of CSV, JSON, Parquet, Excel, SQLite, Delta, Iceberg (metadata file) and DuckLake (local catalog).
   - Each fixture holds a known row count and sum.
   - Two KPI tiles per source, one with `COUNT(*)` and one with the sum, show exactly those values.
10. **Manual sources (owner, internal network).** Postgres, pg_lake, pg_ducklake, S3/SeaweedFS, Iceberg REST and SharePoint are each verified once with a known count and sum. Until a source is verified it is listed as **unqualified** in the skill's reference.

## Settled decisions (owner, 2026-11-24)

1. **Speed:** < 1 s filter / < 5 s load is a soft target (acceptance 6).
2. **Data volume:** the build warns above 25 MB of embedded Parquet.
3. **Repository layout:** the repository is the skill ([ADR 0002](../adr/0002-repository-is-the-skill.md)). The npm package `featherbi` is deprecated, or unpublished where npm allows it.
4. **Explore:** on by default; `explore: false` turns it off.
