# Spec 0001: featherBI v1, a skill that builds single-file BI dashboards

Status: **proposed**, awaiting owner approval.
Architecture: [ADR 0001](../adr/0001-dashboard-stack.md).
Evidence: [research 2026-11-24](../research/2026-11-24-dashboard-stack.md).
Contract: planning-contract v1.

## Goal

featherBI is an agent skill. A user describes the dashboard they want ("revenue by region and month from these files"). The agent writes one **dashboard config**, and deterministic scripts and templates turn that config into an impressive, fast BI dashboard in **one HTML file**. The recipient opens the file by double-click and can filter, cross-filter and explore it without a server.

## Users and flow

1. **The author asks an agent with the skill installed.**
   - The agent profiles the sources with a script that outputs schema and counts.
   - It writes `dashboard.yaml`, which holds the sources, SQL and tiles.
   - It runs `build`. Every step after writing the config is deterministic.
2. **`build` creates the snapshot.** Native DuckDB 2.0.x reads each source, runs the source SQL and writes Parquet. The HTML template, the prebuilt CSS, the renderer and the data then become `dist/<name>.html`.
3. **The recipient opens the file.** Haybarn-Wasm loads the embedded Parquet. Tiles render from SQL, and filters re-run that SQL.

## Scope

### Sources (read at build time only)

- **Files:** CSV, JSON, Parquet, Excel (.xlsx).
- **Table formats:** Delta, Iceberg (file or REST catalog), DuckLake.
- **Databases:** SQLite, Postgres (includes pg_lake and pg_ducklake through Postgres or their S3 data).
- **Object storage:** S3 and S3-compatible stores such as SeaweedFS. Credentials come from the environment or a DuckDB secret, never from the config file.
- **SharePoint/OneDrive:** a file URL or a path in a locally synced folder. Authentication happens before the build and is outside featherBI.

### Outputs

- **Single file (default):** one HTML file with the Parquet data and CSS inlined. JS libraries load from a pinned CDN.
- **`--offline`:** everything is inlined (engine, libraries). The file is large; the size is reported.
- **`--split`:** HTML plus separate `.parquet` files in one folder. For larger data or web hosting.

### Tile types (the agent selects and configures, never codes)

| Type | Use | Built on |
|---|---|---|
| `kpi` | value, comparison and sparkline | SQL + ECharts |
| `echarts` | line, area, bar, stacked bar, pie/donut, scatter, heatmap, treemap, sunburst, funnel, gauge, sankey, waterfall, boxplot, calendar, map (≥ 15 presets) | SQL + ECharts option with data bindings |
| `pivot` | rows × columns with totals | SQL returning `r, c, v` + DaisyUI table |
| `table` | raw or aggregated rows, sort, filter, infinite scroll | AG Grid Community, every interaction runs as SQL |
| `text` | heading, Markdown note | template |

Perspective "Explore" is a navbar button, not a tile. It opens one Perspective viewer on a chosen table, loads only on first open, and takes the current filters when it opens.

### Interaction

- **Global filters:** a date range plus any number of dimension selects. Each one is declared in the config.
- **Cross-filter:** a click on a chart element, heatmap cell or pivot row sets a filter.
- **Filter chips** with remove (×), plus Reset.
- **`exclude`:** each tile can opt out of filtering by its own dimensions.
- **Layout and theme:** responsive (2 columns on desktop, 1 on mobile), light/dark toggle.
- **Safe SQL:** every SQL uses bound parameters for filter values. Identifiers come only from the config's allowlists.

### Config (sketch; the plan fixes the schema)

```yaml
title: Sales overview
sources:
  sales: { read: "read_xlsx('data/sales.xlsx')" }   # any DuckDB table expression
  orders_pg: { attach: "postgres:dbname=shop", table: "public.orders", sql: "SELECT ... " }
dims: { region: {col: region, select: true}, channel: {col: channel, select: true} }
date: { col: order_date, default: last_12_months }
tiles:
  - { type: kpi, title: Revenue, sql: "SELECT SUM(revenue) value FROM sales WHERE {{filters}}", format: currency }
  - { type: echarts, preset: donut, title: Revenue by channel, sql: "...", click: channel }
  - { type: pivot, title: Country × category, sql: "..." }
  - { type: table, source: sales, columns: [order_date, region, revenue] }
```

- `preset` pulls a reviewed ECharts option from the skill's template library.
- An `option` override is allowed, but the preset is the default path.
- The build validates the config against a JSON schema and dry-runs every SQL against the snapshot. It fails with a precise error before writing any HTML.

### Determinism

- **Same output:** the same config, the same input data and the same skill version produce a byte-identical HTML file. That means fixed ordering, no timestamps in the output, and pinned library versions.
- **Prebuilt CSS:** the DaisyUI/Tailwind CSS is built when the skill is released and shipped with the skill. Building a dashboard does not need npm or Tailwind.
- **Build requirements:** the DuckDB CLI ≥ 2.0 and Node ≥ 22 (no npm install).

## Non-goals (v1)

- Live loading in the browser. That is v2: Iceberg, DuckLake and S3 per source, maybe Grainlift for Postgres.
- A server, scheduled refresh, or authentication inside the dashboard. A refresh is a rebuild.
- Editing dashboards in the browser, or saving viewer state.
- A CLI or npm package as a product. The skill with its scripts is the product.
- A theme engine. Only light and dark, with one default design.
- Other chart libraries, Mosaic, Plotly.
- Specs, ADRs or process beyond what this spec and ADR 0001 need.

## Acceptance examples

1. **Local test data.**
   - Input: a generated dataset of 1 M synthetic sales rows (Parquet) and a small Excel file with targets per region.
   - The agent is asked for "revenue by region and month, with targets".
   - Expected output:
     - one `dashboard.html` with ≥ 4 KPIs, ≥ 3 ECharts tiles, 1 pivot, 1 table;
     - a date filter, region and channel selects, and cross-filter by click.
2. **Opening.** The file opens by double-click (`file://`) in current Chrome and Firefox. Every tile renders and the console shows no errors.
3. **Speed.** On the owner's machine, filter changes and cross-filter clicks render all tiles in **< 1 s**, measured from the second filter change onward (median of 5). Initial load is **< 5 s** on a warm CDN cache.
4. **Determinism.** Two builds from the same inputs produce identical SHA-256 hashes.
5. **Config errors.** An invalid config, such as an unknown column, an unknown preset or SQL that fails, stops the build with an error that names the tile and the problem. No HTML is written.
6. **Snapshot sources.** A build from CSV, JSON, Parquet, Excel, SQLite, a Delta table and an Iceberg table, all local fixtures, succeeds. Postgres and S3 are verified later against the owner's internal servers; that is a manual test outside CI.

## Open decisions (block the plan)

1. **Speed target.** < 1 s replaces the earlier < 200 ms target, which round 3 did not reach on the test host. Do you accept this?
2. **Data volume limit for single file.** Proposal: warn above 25 MB of embedded Parquet. Recommend `--split` or build-time aggregation.
3. **Repository layout.** Proposal:
   - this repo is the skill: `skill/featherbi/` with `SKILL.md`, scripts, templates and references;
   - it installs with `npx skills add legout/featherbi`;
   - the npm package `featherbi@0.3.0` is deprecated with a pointer to the repo.
4. **Explore by default.** Proposal: on, with a config switch `explore: false`.
